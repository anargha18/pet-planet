# Implementation status

> **Warning (2026-11-13):** The "Implemented" labels below describe code that exists, not verified end-to-end behavior. The [restructuring audit](../restructuring/01-audit-findings.md) found blockers that stop these features working at runtime. Seeded logins (F1) and browser CORS for auth (F2) were fixed and verified on 2026-11-14 (Phase 0b). Cross-service Kafka delivery (F3) was fixed and verified on 2026-11-14 (Phase 1): a new order reaches `PAID` in about 1 s, with payment, shipment, delivery, fulfillment and notification records and catalog `SOLD`. Compensation paths (cancel, payment failure, expiry, sale conflict, archive rules) were fixed in Phase 2 and verified by `make smoke` (22/22 checks) on 2026-11-14. Downstream boundaries (one delivery action, shipment mirroring, typed notifications, fulfillment tracking projection) were built in Phase 4 and verified by `make smoke` (74/74 checks) on 2026-11-15. It also found saga gaps (S1, S2, S5, S7, S9). This table will be rewritten as the [restructuring phases](../restructuring/02-target-architecture-and-requirements.md#4-implementation-phases-order-matters) land.

## Feature status (Post-Refactoring)

| Feature | Status | Evidence and qualification |
|---|---|---|
| API Gateway (`gateway-service`) | Implemented and verified (2026-11-14, Phase 3) | Spring Security WebFlux resource server: validates RS256 JWTs (user-service issues them) with the shared `PlatformJwt` contract, applies only coarse role rules, never routes `/internal/**`, and has no ownership callout. Verified by `GatewaySecurityTest` and the smoke test's security scenario. |
| Service-level authentication and ownership (Phase 3) | Implemented and verified (2026-11-14) | All 9 servlet services validate the JWT themselves (platform-commons resource server; no JJWT copies). Order, payment, notification, shipping, delivery-tracking and fulfillment reject another customer's records with 403 (admins see all). Controllers return DTOs; every error uses the shared `ApiError` body. Verified by per-service tests and live by `make smoke` scenario S. Payments created before payment `V4` have no owner and are admin-only. |
| User management and authentication | Implemented | User-service owns BCrypt credentials, integer-ID user CRUD, and RS256 token issuance; the gateway only validates tokens. User accounts support self profile/password updates, admin CRUD, and soft deactivation; default `ADMIN` and `USER` accounts are seeded/migrated by Flyway. |
| Internal service boundary | Implemented for local Compose | Backend HTTP ports are not published; user-service requests require a shared gateway token, generated into `.env` by `scripts/generate-dev-keys.sh` (no secrets in git; the pre-Phase-3 dev key remains in git history). Production mTLS is still an infrastructure deployment requirement, not configured here. |
| Pet catalog CRUD/search & sync | Implemented and verified (2026-11-14) | Seeded with 6 sample pets. `availabilityStatus` is a read-only copy synced from inventory. `DELETE` archives (`RETIRED`, hidden, not orderable; 409 for reserved/sold pets). Catalog events go through an outbox. |
| Order create/list/get/cancel & Saga | Implemented and verified (2026-11-14) | `OrderStateMachine` (`CREATED → PAYMENT_PENDING → CONFIRMED`; `CANCELLED`/`FAILED` terminal). Confirmed only after inventory sold the pets (`PetsSold`). Every unsuccessful ending publishes `OrderCancelled`/`OrderFailed`. Smoke-tested: happy path, payment declined, cancel during charge, expiry during charge. |
| Inventory reserve/expiry/sold | Implemented and verified (2026-11-14) | All-or-nothing reservation (unknown pets fail with `PET_NOT_FOUND`). Sells on payment **only if still reserved for the order**, otherwise reports `InventorySaleConflict` (no double sale). Releases on `OrderCancelled`/`OrderFailed`, configurable expiry, `RETIRED` for archived pets, read-only HTTP. |
| Payment | Implemented and verified (2026-11-14) | Charges the order total through a simulated `PaymentGateway` (no fallback amount). Refunds a successful charge when the order is cancelled or failed (`REFUNDED`, `PaymentRefundedEvent`) and never charges a closed order. Per-order advisory lock prevents charge/cancel interleaving (smoke-tested with slow charges). |
| Delivery tracking & shipping (Phase 4) | Implemented and verified (2026-11-15) | One admin action `PUT /api/v1/deliveries/order/{id}/status` (`IN_TRANSIT → OUT_FOR_DELIVERY → DELIVERED / DELIVERY_FAILED`, illegal moves 409) with a delivery timeline; shipping only creates shipments and mirrors delivery status (no mutation API). Verified by unit/slice tests and `make smoke` (scenarios 1 and D). |
| Notifications (Phase 4) | Implemented and verified (2026-11-15) | Typed notifications, one per order and type: `ORDER_CONFIRMED`, `ORDER_CANCELLED`, `ORDER_FAILED`, `PAYMENT_REFUNDED`, `SHIPPED`, `OUT_FOR_DELIVERY`, `DELIVERED`, `DELIVERY_FAILED`; list endpoints per order, per customer and `/me`. Sending is simulated (stored and marked `SENT`). Verified by `make smoke`. |
| Order-tracking projection (fulfillment, Phase 4) | Implemented and verified (2026-11-15) | CQRS read model from 12 topics with a per-order timeline, monotonic status updates and escalation (delivery failure; stuck before confirmation after `FULFILLMENT_STUCK_AFTER`). Rebuilt from Kafka history on first start (matched order-service: 16 orders). The stuck-order escalation is covered by a unit test only; it was not observed live. |
| Transactional outbox + Kafka conventions | Implemented and verified (2026-11-14) | All 7 producing services (catalog, order, inventory, payment, notification, shipping, delivery-tracking; fulfillment stopped producing in Phase 4) write outbox rows only. The shared `platform-commons` relay publishes after broker acknowledgement. Consumers use plain JSON, retry, then dead-letter to `<topic>.DLT` (verified live with a poison message), and deduplicate via `processed_events`. See [Event catalog](./events.md). |
| React storefront (Phase 5) | Implemented and verified (2026-11-15) | One axios client with token and 401 interceptors (expired session → `/login?expired=1`); `ProtectedRoute`/`AdminRoute` and a role-aware nav; profile and password change; orders list from the tracking projection; order page with timeline, notifications and 2 s polling after checkout; simulated payment stated; admin pages for pets, inventory (read-only), orders, users and deliveries. Verified by build, boundary check and a 29-check headless-Chrome walkthrough. No automated frontend tests are in the repository. |
