# CLAUDE.md

Instructions for AI coding assistants working in this repository. This is the only AI instruction file; do not add others (no `AGENTS.md`, no extra memory folders in the repo).

## Project in one paragraph

Pet Planet is an event-driven pet shop for learning microservices: 10 Spring Boot 3.5.5 / Java 17 services (gateway + 9 domain services) at the repository root, a shared infrastructure library `platform-commons`, Kafka 4.0.1, one PostgreSQL 16 database per service, and a React 18 / Vite storefront in `frontend/`. Checkout is a choreographed saga (order → inventory → payment) with compensation, a transactional outbox and idempotent consumers.

## Documentation

All project documentation lives in [`docs/`](docs/README.md), and only there. Start at `docs/README.md`.

Before a task:
1. Read `docs/README.md` and the chapters relevant to the task.
2. Check the source code, because it and the Flyway migrations are the primary evidence. If the docs disagree with the code, trust the code and fix the docs.

After a change:
1. Update the affected chapter(s) in the same change when architecture, schema, events, APIs, security, frontend behavior, configuration, infrastructure, tests or status change.
2. Document new tables, columns, constraints and migrations in `docs/06-database.md`. Document new or changed endpoints in `docs/05-api-reference.md`, and new topics or payload fields in `docs/03-events-and-saga.md`.
3. Never describe planned or partly implemented work as done. Put open items in `docs/12-status-decisions-and-known-issues.md`.
4. Don't rewrite unrelated documentation, and don't edit docs when behavior didn't change.
5. Keep relative links working, and keep the chapter table in `docs/README.md` accurate.
6. At the end, report which docs you changed and anything you could not verify.

## Code rules

- Follow the package layout in [`docs/09-code-structure-and-patterns.md`](docs/09-code-structure-and-patterns.md): `api` (controller/dto/mapper/error) · `application` · `domain` (model/policy/exception) · `security` · `messaging` (event/consumer/publisher) · `persistence` (entity/repository) · `client` · `config`. Services stay at the repository root.
- Services never import each other's classes. Share only JSON/HTTP contracts and `platform-commons` (infrastructure only, with no domain or event classes).
- Events are written through the service's outbox inside the business transaction, never sent directly with `KafkaTemplate`. Consumers must be idempotent. Never add fallback values for required event fields.
- Order status changes only through `OrderStateMachine`. Inventory owns availability; the catalog only mirrors it.
- **Never edit an applied Flyway migration.** Add a new `V<n>__*.sql`.
- Never commit secrets. `.env` is generated by `scripts/generate-dev-keys.sh`.

## Checks to keep green

```sh
./mvnw test                              # all backend tests incl. ArchUnit (Docker needed for Testcontainers)
./mvnw -pl <service> -am test            # one service (-am builds platform-commons)
cd frontend && npm run build && npm run check:boundaries
make smoke && make ui-check && make e2e  # end-to-end, with the stack running (make up); Playwright guide: docs/13-playwright-e2e.md
```

## Environment notes

- The shell is zsh: an unquoted `$VAR` holding a list is not word-split.
- After a frontend change, run `docker compose up -d --build frontend` (the image copies the source).
- Postgres superuser: `petplanet_admin` (`docker exec -it pet-planet-postgres psql -U petplanet_admin -d <db>`).
- More gotchas: `docs/10-infrastructure-and-operations.md#troubleshooting` and `docs/12-status-decisions-and-known-issues.md#environment-gotchas`.
